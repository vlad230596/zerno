# Разделение счёта: чек → доли → долги

Статус: **черновик, не реализовано.**
Связано: [composite-operations.md](./composite-operations.md) — фундамент, делается раньше;
[auto-categorization.md](./auto-categorization.md)

## Сценарий

Плачу за обед на компанию: 10 000 ₽ одной картой, из них моя доля — 1 500 ₽,
остальное за пятерых друзей. Хочу:

1. В бюджете за этот месяц видеть расход **1 500 ₽** по категории «Кафе», а не 10 000 ₽.
2. Видеть, кто сколько должен и кто уже вернул.
3. Когда придёт перевод от Пети — чтобы он погасил именно долг Пети.
4. В идеале — загрузить чек и разложить позиции по людям, чтобы доли посчитались сами.

## Почему здесь долги, а не составная операция

Первоначально хотелось склеить расход и все входящие переводы в одну операцию с общим
итогом. Довод против, который тут стоял раньше, был **преувеличен** и исправлен: см.
[composite-operations.md](./composite-operations.md), раздел «Как это влияет на расчёты».
Коротко: месяцы считаются цепочкой от текущих реальных остатков назад в прошлое, и
перенос активности между месяцами сдвигает не всю историю, а только границу между
частями события — месяцы до самой ранней части остаются точными. Составные операции
согласованы и этот сдвиг принимают сознательно.

Для **этого** сценария долги всё равно остаются правильным механизмом, но по другой
причине: составная операция собирается только из уже случившихся операций, а долг живёт
ровно в том промежутке, когда деньги ушли, а обратно ещё не пришли. Пока Петя не вернул,
склеивать нечего. Плюс деньги за друзей физически покидают бюджет, и долговой счёт вне
бюджета это отражает без единой правки в расчётах.

Разделение счёта делается **поверх** составных операций и после них.

### Как долг устроен сейчас

Долг — это не отдельная запись, а **производная от транзакций** на долговом счёте
(`accountModel.getDebtAccountId`):

- `TrType.OutcomeDebt` (деньги ушли **в** долговой счёт) → `balance += outcome`, человек должен мне
- `TrType.IncomeDebt` (деньги пришли **из** долгового счёта) → `balance -= income`, человек вернул

Долговой счёт вне бюджета (`inBudget: false`), поэтому 8 500 ₽ за друзей не размазываются
по конвертам — они висят долгом. В бюджете остаётся только моя доля. Месяц при этом
никуда не «фиксируется»: конверт «Кафе» видит ровно 1 500 ₽ в апреле, и это правда.

## Что нужно построить

### 1. Действие «Разделить счёт»

Точка входа — контекстное меню транзакции и `TransactionList/TopBar/Actions.tsx`.
Берём один расход и раскладываем его на:

- **мою долю** — остаётся исходной транзакцией, сохраняет категорию и счёт
- **N долгов** — по транзакции на каждого участника: с того же счёта на долговой,
  `merchant` или `payee` = имя участника

Сумма долей обязана сойтись с исходной суммой; UI не даёт сохранить иначе.
Режимы деления: поровну, по долям (Петя за двоих), вручную, по позициям чека.

### 2. Черновик разделения

Пока счёт не разделён окончательно, состояние живёт в hidden-store
([`5-entities/shared/hidden-store`](../../src/5-entities/shared/hidden-store),
новый `HiddenDataType.SplitDrafts`, помесячный стор по дате исходной транзакции):

```ts
type TSplitDraft = {
  id: string
  sourceTrId: TTransactionId   // исходный расход
  title: string                // «Обед 12.09»
  participants: Array<{
    id: string
    name: string               // «Петя»
    amount: number
    lines?: string[]           // id позиций чека, если делили по чеку
    debtTrId: TTransactionId | null  // созданная долговая транзакция
  }>
  myShare: number
  changed: TMsTime
}
```

После применения черновик можно удалить — дальше всё живёт в обычных транзакциях,
и долги считаются существующим `getDebtors`. Черновик нужен только чтобы
не терять раскладку по позициям чека и уметь переразделить.

### 3. Сопоставление входящих переводов с долгами

Самая ценная часть. Приходит перевод — предложить погасить им долг:

- сумма совпадает с открытым долгом (точно или близко)
- имя плательщика похоже на должника — через `cleanPayee`, как в `getDebtors`
- дата в пределах N дней от исходного расхода

По подтверждению транзакция переписывается: `outcomeAccount` → долговой счёт,
то есть перевод превращается в `IncomeDebt` и гасит долг.

Где показывать: чип прямо на строке входящей транзакции в списке + сводка
непогашенных долгов.

### 4. Позиции чека — отдельная и последняя задача

**Ограничение:** в QR-строке чека позиций нет физически. Товарная часть живёт в API ФНС,
для которого нужна авторизация пользователя (ИНН + пароль от личного кабинета),
это работает только в России и требует запроса к чужому сервису.

Поэтому по возрастанию сложности:

1. деление поровну / по долям / вручную — **это и есть v1**
2. ручной ввод позиций (название + цена + кому), раскладка по людям
3. интеграция с API ФНС по `fn`/`i`/`fp` из уже сохранённого QR
4. распознавание фото чека

Модель `participants[].lines` рассчитана на (2)–(4), но не требует их.

## Открытые вопросы

- **`keepIncome` для долговых конвертов.** В
  [`makeEnvelope.ts:168`](../../src/5-entities/envelope/shared/makeEnvelope.ts) он по умолчанию
  `false`, значит возврат долга в `2 - activity.ts` уходит в общий доход, а не гасит
  конверт должника. В боковой панели месяца (`2 - sortedActivity.ts`) долги схлопываются
  правильно, но в таблице конвертов — надо проверить на реальных данных.
- Что делать, если человек вернул не всю сумму или больше. Долг просто останется ненулевым —
  вероятно, этого достаточно.
- Нужна ли отдельная страница «Кто мне должен» или хватит существующего `DebtorList`.

# Импорт чеков из «Мои чеки онлайн»

Статус: **разведка закончена, кода нет.**
Связано: [ozon-import.md](./ozon-import.md), [composite-operations.md](./composite-operations.md),
[split-bill.md](./split-bill.md)

Чеки — второй источник состава покупки после [заказов Ozon](./ozon-import.md). Он
закрывает то, чего Ozon не видит: продуктовые магазины, кафе, такси, аптеки,
заправки. То есть повседневные траты, которых в списаниях больше всего и понятно
про них меньше всего.

Источник ровно один — личный кабинет ФНС `lkdr.nalog.ru`. Почему не два и почему
не пять, разобрано ниже.

## Почему lkdr, а не Едадил и не разбор QR

Изначально окон казалось два: кабинет ФНС и приложение Едадил, через которое чеки
сканируются. Проверка показала, что это **два окна в один и тот же пул данных**, а
не два источника.

Чеки приезжают в Едадил из ФНС (`features: ["provider.fns.electro"]`), а сканы,
сделанные в Едадиле, видны в lkdr как `sourceCode: SCAN_PARTNER`. Сравнение одного
и того же чека Магнита в обеих системах:

| | lkdr | Едадил |
|---|---|---|
| Позиций в чеке | **13** | 11 |
| Количество | `1.659` (кг) | `1` — округлено до штук |
| НДС, тип товара, коды маркировки | есть | нет |
| Размер страницы | до 5000 | **20**, при 50 уже `400` |
| Полная выгрузка | 1 запрос | ~160 страниц + запрос на каждый чек |

Позиции у Едадила — та же сырая фискальная строка, без нормализации названий и без
товарных категорий. Ради словаря «ИНН → человеческое имя сети» держать вторую
интеграцию не стоит: его дешевле снять один раз и положить в репозиторий.

Остальные пути отпадают по одной общей причине — **все они работают от уже
известного QR-кода**:

| Путь | Почему не подходит |
|---|---|
| Приложение «Проверка чеков» ФНС (`irkkt-mobile.nalog.ru:8888`) | Умеет «проверь вот этот QR», а не «покажи мои чеки за вчера» |
| Кабинеты ОФД (ofd.ru, Первый ОФД, Такском) | Покрытие рваное — только кассы этого оператора |
| Платные прокси (proverkacheka.com и подобные) | Нужен QR, и за деньги |
| Свой разбор QR-строки — [`receipt.ts`](../../src/6-shared/helpers/receipt.ts) | Поле `qrCode` заполнено у **0 транзакций из 8302**. Код парсит то, чего нет |

## Что отдаёт API

Два эндпоинта, оба `POST`, оба на своём же origin. Авторизация — заголовок
`Authorization: Bearer <токен>`, токен лежит в `localStorage`, а не в куке.

### Список

```
POST /api/v1/receipt
{"limit":10,"offset":0,"dateFrom":null,"dateTo":null,
 "orderBy":"CREATED_DATE:DESC","inn":null,"kktOwner":""}
```

Ответ: `{receipts, brands, hasMore, totalCount, page, limit, offset}`.

Веб-морда ходит с `limit: 10` и кнопкой «Показать ещё». **Это ограничение
интерфейса, а не API.** Живой прогон: `limit: 5000` отдал **всю историю одним
запросом за 3,2 секунды** — 3177 чеков с 03.01.2018 по 18.09.2026, `hasMore: false`,
`totalCount: 3177`. Ни курсоров, ни переезжающих полей продолжения, ни перебора
годов — ничего из того, что пришлось обходить на [Ozon](./ozon-import.md#как-устроен-обход).

Поля чека: `key`, `createdDate`, `receiveDate`, `totalSum`, `kktOwner`, `kktOwnerInn`,
`buyer`, `buyerType`, `fiscalDocumentNumber`, `fiscalDriveNumber`, `brandId`,
`sourceCode`, `receiptState`, `complaints`, `favorite`.

Фильтр `dateFrom` / `dateTo` — строки `YYYY-MM-DD`, **обе границы включительно**
(проверено на диапазоне 17–19 сентября: вернулось ровно 5 чеков, включая оба крайних
дня).

### Позиции

```
POST /api/v1/receipt/fiscal_data
{"key":"<buyer>|<buyerType>|<createdDate>|<fiscalDocumentNumber>|<fiscalDriveNumber>"}
```

`key` приходит готовым в каждом элементе списка — собирать его руками не надо.

| Поле позиции | Пример |
|---|---|
| `name` | «Филе грудки цыплёнка-бройлера Приосколье» |
| `price`, `quantity`, `sum` | `429.99`, `1.659`, `713.35` |
| `nds`, `ndsSum` | ставка и сумма налога |
| `productType`, `itemsQuantityMeasure` | тип предмета расчёта, единица измерения |
| `productCodeNew` | GTIN и серийный номер — у маркированных товаров |

В шапке кроме суммы и продавца: `retailPlace`, `retailPlaceAddress`, `kktRegId`,
`operationType`, `internetSign` и — важное для сопоставления —
**`cashTotalSum` / `ecashTotalSum`**.

## Ловушки

Первая — в породе тех, что описаны в [ozon-import.md](./ozon-import.md): не падает
с ошибкой, а молча отдаёт пустоту как правду.

1. **`limit: 1` возвращает `200` и пустой список.** При этом `totalCount: null`,
   `hasMore: false` — выглядит как «чеков нет». С `limit: 2` тот же запрос отдаёт
   2 чека и `totalCount: 3177`. Пробник, написанный на одном чеке, соврёт.
2. **Позиции есть только с декабря 2020.** Обход по первому чеку каждого месяца:
   всё до `2020-11` включительно отдаёт **422**, всё с `2020-12` — **200**. Граница
   идеально чистая, это дата запуска самого сервиса. В списке старые чеки лежат
   (сумма, продавец, ИНН), товарной части у них нет и не появится. Под это попадает
   ~865 чеков из 3177 — вся история 2018–2020.
3. **`receiveDate` бывает раньше `createdDate`** — у 10 чеков 2026 года. Разницу
   считать со знаком и не падать на отрицательной.

### Справочник брендов

В ответе списка рядом с чеками приходит `brands` — 37 записей вида
`{id, name, description, image}`, где `description` это **категория продавца**:
«Супермаркет», «Заказ такси», «Аптека», «Платные дороги», «Торговля техникой».

Покрытие слабое и падает: `brandId` проставлен у 1995 чеков из 3177, а за 2026 год —
только у **252 из 755**. Справочник ФНС не поспевает за новыми сетями; Магнит,
Бургер Кинг и КДВ в него не попали. Рассчитывать на него как на источник категории
нельзя — разве что как на бесплатную подсказку там, где он сработал.

## Режим догрузки

Задержка `receiveDate − createdDate` по всем 755 чекам 2026 года:

| Задержка | Чеков |
|---|---|
| меньше часа | 661 |
| 1–6 ч | 64 |
| 6–24 ч | 13 |
| 1–3 суток | 5 |
| больше 3 суток | 2 |

Медиана — 0 часов, p90 — 3 часа, p99 — сутки, максимум — 102 часа.

Отсюда рабочий режим: **один запрос в день с `dateFrom = сегодня минус 5 дней`**.
Это ловит всё с запасом и стоит 1 запрос списка плюс 5–10 запросов позиций.

Стоимость запросов асимметрична, и это определяет весь порядок работы:

| Операция | Время |
|---|---|
| Список целиком (3177 чеков) | 3,2 с |
| Позиции одного чека | ~1,1 с |

Полный бэкфилл товарной части (~2300 чеков с декабря 2020) — около часа фоновой
работы, разово. Открытые клиенты ставят паузу 80 мс между запросами; `429`
приходит с `Retry-After`. В режиме догрузки в лимиты упереться невозможно.

## Авторизация

Вход по номеру телефона с кодом из СМС, плюс **Yandex SmartCaptcha** на странице
логина — чекбоксом, в iframe `captcha-api.yandex.ru`. Автоматизировать вход нельзя
и не нужно: человек логинится руками раз в сессию.

После входа в `localStorage` появляются `auth.token`, `refresh.token`,
`auth.token.expires` и `sourceDeviceId`, а среди вызовов страницы есть
`POST /api/v1/auth/token`. То есть тихое продление сессии предусмотрено самим
сервисом. Единственный открытый клиент
([TumanovNV/fns-receipt-parser](https://github.com/TumanovNV/fns-receipt-parser))
этого не умеет и ловит `401` посреди длинной выгрузки — нам чинить дешевле, чем
ему.

## Сопоставление с транзакциями

В отличие от [заказов Ozon](./ozon-import.md#сопоставление-с-транзакциями), где
между списанием и чеком проходит до трёх недель, здесь **фискальная дата и есть
момент оплаты**. Окно нужно узкое, а не ±21 день.

Два поля решают половину работы заранее:

- **`cashTotalSum > 0`** — чек оплачен наличными. Среди банковских операций его
  искать бессмысленно, и это видно до всякого перебора.
- **`ecashTotalSum`** — сумма, которая должна найтись в списаниях. Она не всегда
  равна `totalSum`: остаток может быть предоплатой (`prepaidSum`), кредитом
  (`creditSum`) или встречным предоставлением (`provisionSum`).

Точность сопоставления на реальных данных **не измерена** — это первое, что нужно
сделать перед кодом.

## Куда встраивается

- **Модель.** Чек — это событие из
  [composite-operations.md](./composite-operations.md): вход — списание, выходы —
  позиции. Ровно так же, как заказ Ozon. Своего типа заводить не нужно.
- **Хранилище.** Новый `HiddenDataType` поверх
  [`makeMonthlyHiddenStore`](../../src/5-entities/shared/hidden-store/monthlyStoreFactory.ts):
  3177 чеков в простой стор не поместятся.
- **Обязательный побочный эффект.** Создание события ставит входу исключение из
  правил, иначе автокатегоризация перетрёт теги под событием.
- **[Разделение счёта](./split-bill.md).** Пункт «ручной ввод позиций чека» из плана
  этой фичи закрывается автоматически: позиции приезжают готовыми. Остаётся только
  раскладка по людям.
- **Категоризация.** Названия позиций — сырые строки от кассы. Как и сказано в
  [ozon-import.md](./ozon-import.md#почему-ozon-а-не-чеки-фнс), для
  [правил](./auto-categorization.md) они непригодны без чистки. Чеки дают **состав**
  покупки, а не материал для автокатегоризации.

## Доставка данных

Ограничение то же, что у [Ozon](./ozon-import.md#доставка-данных): у zerno нет
бэкенда, браузер ходит только в ZenMoney API, сходить в ФНС из приложения мешает
CORS. Значит код исполняется в контексте страницы `lkdr.nalog.ru`, а zerno
принимает готовый JSON — тем же путём, что и заказы.

Разница в пользу чеков: антибота нет, данные приходят плоским JSON, схему виджетов
снимать не нужно. Капча — только на входе.

## Что осталось выяснить

- Точность сопоставления по сумме и дате на реальных данных: какой процент чеков
  находит свою транзакцию и в каком окне.
- Как выглядят возвраты. `operationType` различает приход и возврат прихода, но на
  данных это не проверялось — в сумму 4,6 млн ₽ возвраты сейчас входят со знаком
  плюс.
- Что делать с чеками до декабря 2020: хранить как шапку без позиций или не
  импортировать вовсе.
- Совпадают ли чеки Ozon из ФНС с заказами из
  [ozon-import.md](./ozon-import.md) — и не создадут ли два импорта два события на
  одну покупку.
- Снимать ли из Едадила словарь «ИНН → имя сети», чтобы закрыть дыру в справочнике
  `brands` ФНС.

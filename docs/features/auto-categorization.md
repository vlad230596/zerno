# Правила категоризации («живая» разметка)

Статус: **реализовано.**
Связано: [split-bill.md](./split-bill.md)

## Сценарий

Ozon раньше попадал в «Продукты». Решаю, что это «Маркетплейсы»:

1. Открываю одну операцию Ozon, ставлю ей новую категорию.
2. Жму ✨ **«Создать правило категоризации»** в шапке карточки.
3. В диалоге вижу условие (магазин, текст в месте платежа, текст в
   комментарии), категорию и live-превью: сколько операций **за всю историю**
   подходит и какие именно.
4. Сохраняю — правило сразу переразмечает прошлое и дальше работает само после
   каждой синхронизации.

Если позже поправить категорию у одной конкретной операции руками, эта правка
остаётся навсегда: правило больше её не трогает.

## Как это устроено

### Почему метаданные не лежат на транзакции

Транзакция синкается с сервером как есть (`state.current = state.server`,
[`store/data/slice.ts`](../../src/store/data/slice.ts)) — сервер может целиком
заменить объект. Поэтому «кто и когда поставил тег» хранится отдельно, в скрытом
хранилище: два стора через `makeSimpleHiddenStore`
([`hidden-store`](../../src/5-entities/shared/hidden-store)) с новыми типами
`HiddenDataType.Rules` и `HiddenDataType.RuleState`.

### Модель — [`5-entities/rule`](../../src/5-entities/rule)

```ts
type TRule = { id: string; condition: TrCondition; tags: TTagId[] }
```

Условие — это существующий `TrCondition` из
[`transaction/filtering.ts`](../../src/5-entities/transaction/filtering.ts), тот
же язык, на котором работает поиск операций. Никакого отдельного языка условий
нет: `merchant`, `payeeText`, `mcc`, комбинации через `or`/`and` доступны сразу.
Порядок массива правил = приоритет, индекс 0 — высший.

Состояние отслеживания — `Record<TTransactionId, TRuleTrack>`, где
`TRuleTrack = { ruleId, tags } | 'excluded'`.

### Движок — [`ruleEngine.ts`](../../src/5-entities/rule/ruleEngine.ts)

Единственная точка входа — `runAllRules()`. Для каждой операции (только доходы и
расходы; переводы и долги пропускаются):

1. `'excluded'` — не трогаем никогда.
2. Есть трек, но теги операции ему не равны → категорию поменяли руками →
   помечаем `'excluded'` навсегда и тег не трогаем.
3. Иначе ищем первое подходящее правило по порядку. Нашли и теги отличаются —
   патчим через `applyClientPatch`, записываем новый трек.
4. Не нашли — удаляем трек, тег оставляем как есть.

Ключевое решение: **факт ручного вмешательства определяется диффом с прошлым
запуском**, а не хуками в `applyChangesToTransaction`/`bulkEditTransactions`.
Движок не зависит от того, каким путём отредактировали тег, и существующая
логика транзакций не меняется. Если ничего не изменилось, стор не пишется — так
синхронизация не начинает молотить сама себя.

`createRule` / `updateRule` / `deleteRule` / `reorderRules` меняют список и сразу
вызывают `runAllRules()`.

### Применение вперёд

В [`4-features/sync.ts`](../../src/4-features/sync.ts) сразу после
`applyServerPatch` вызывается `ruleModel.runAllRules()` — единственная правка в
существующем файле синка. Сработавшие изменения уезжают на сервер обычным
диффом, так что категория появится и в мобильном ZenMoney.

Правило **перетирает** уже проставленную категорию (в том числе присвоенную
ZenMoney при импорте) — иначе исходная задача не решается: проценты по вкладу
приходят с категорией «Кафе и рестораны», а не пустыми. Защита от откатов ручных
правок — механизм `'excluded'`, описанный выше.

### UI

Условие предзаполняется так, чтобы **исходная операция всегда попадала в
фильтр** — иначе пользователь получает правило, которое ничего не находит, и
никакого объяснения. Приоритет: магазин и место платежа (это «с кем» операция), а
комментарий — только когда ни того, ни другого нет: у банковских операций вроде
выплаты процентов больше зацепиться не за что. Комментарий описывает саму
операцию, а не контрагента, поэтому правило на нём легко перелавливает лишнее.

Категория предлагается только подходящая по типу. В Дзен-мани у категории есть
флаги `showIncome`/`showOutcome`, и пикер их учитывает — а правило проставляет
категорию мимо пикера. Поэтому `getRuleTagType` определяет тип по подходящим
операциям и передаёт его в `TagList`; у уже существующего правила с категорией
не того типа показывается предупреждение. Без этого движок молча писал доходы в
расходную категорию — Дзен-мани такую для доходов даже не показывает.

Важно: `payeeText`/`commentText` — это обычный поиск подстроки без учёта
регистра (`checkTextField` в `filtering.ts`). Значение должно попадать в условие
ровно таким, как оно лежит в транзакции. Прогонять его через `cleanPayee` (он
убирает пробелы и пунктуацию) нельзя — условие перестанет находить вообще что
угодно. Инвариант закреплён тестом
[`condition.test.ts`](../../src/4-features/transactionRules/condition.test.ts).

- **Создание** — только из карточки операции
  ([`TransactionPreview`](../../src/3-widgets/transaction/TransactionPreview/index.tsx)),
  кнопка ✨ в шапке. Диалог —
  [`4-features/transactionRules/RuleModal.tsx`](../../src/4-features/transactionRules/RuleModal.tsx),
  он же работает в режиме редактирования (`rule` вместо `seedTransaction`).
  `conditionToDraft` разбирает условие обратно в галочки формы; условие, которое
  форма выразить не может, показывается read-only, редактируются только теги.
- **Страница `/rules`** — [`2-pages/Rules`](../../src/2-pages/Rules/index.tsx):
  список с человекочитаемым описанием условия, drag-and-drop приоритета на
  `@dnd-kit/core`, редактирование и удаление.
- Live-превью показывает всё, что подходит под условие. Ранее исключённые
  операции в него попадают, но правило их не изменит — превью отвечает на вопрос
  «что подходит под условие», а не «что сейчас поменяется».

## Что осталось

- **«Выделить похожие»** в контекстном меню
  ([`TrContextMenu.tsx`](../../src/3-widgets/global/TrContextMenu.tsx)) по-прежнему
  фильтрует по `tr.changed`, то есть «изменённые в тот же миллисекунд», а не
  операции того же магазина. Название вводит в заблуждение; для «всех операций
  магазина» есть поиск `@место` в шапке списка.
- Удаление правила не откатывает уже проставленные категории — движок просто
  перестаёт за ними следить. Это осознанное поведение.
- Правила по MCC технически уже работают (`mcc` — обычное поле `TrCondition`), но
  в форме создания их нет.
- Одноимённые категории верхнего уровня в списках неразличимы: и пикер
  ([`TagSelect2`](../../src/5-entities/tag/ui/TagSelect2.tsx)), и чип
  ([`TagChip`](../../src/5-entities/tag/ui/TagChip.tsx)) рисуют короткий `name`,
  игнорируя `uniqueName`, а тот и сам различает только через родителя. Диалог
  конверта теперь предупреждает, что название занято, но уже существующие
  дубли всё равно выглядят одинаково.
- `RuleState` хранит запись на каждую затронутую операцию. При очень больших
  историях JSON в `comment` напоминания может стать заметным — тогда состояние
  придётся сжимать (например, хранить теги один раз на правило).
